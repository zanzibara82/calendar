# Мой календарь

Android-календарь на Kotlin и Jetpack Compose: месяцы, недели и дни, события с напоминаниями,
повторами, метками, текстовыми и голосовыми заметками. События хранятся локально (Room) и
синхронизируются с **Google Календарём** через системный провайдер и с **Яндекс Календарём** по
CalDAV — в обе стороны.

Главное отличие от «ещё одного календаря» — **сохранность данных при конфликтах**: приложение
помнит последнее согласованное с облаком состояние каждого события, поэтому правки с двух сторон
не затирают друг друга, а раскладываются по полям и разбираются пользователем.

## Возможности

**Календарь**
- три режима: месяц, неделя, день; перелистывание по периодам, отметки дней с событиями;
- выбор нескольких напоминаний на событие: 5, 10, 15, 30 минут, час, день;
- повторы: ежедневно, еженедельно, ежемесячно, ежегодно;
- метки событий (день рождения, свидание, кино, врач, лекарства, отпуск), текстовые заметки
  и голосовые заметки (M4A,
  остаются на устройстве и не уходят в облако).

**Напоминания**
- точные будильники через `AlarmManager`; после перезагрузки расписание восстанавливается;
- уведомление с действиями «Открыть» и «Отложить» (на 10 минут); на заблокированном экране
  показывается полноэкранное напоминание, если пользователь выдал разрешение;
- экран разрешений: уведомления, микрофон, календарь, точные будильники, полноэкранные уведомления.

**Оформление**
- светлая, тёмная и системная тема по фиксированной палитре (без динамических цветов Material You);
- выбор хранится в DataStore.

**Синхронизация**
- Google — через `CalendarContract`, без OAuth: достаточно аккаунта Google на телефоне и
  разрешения на доступ к календарю;
- Яндекс — OAuth (`mycalendar://oauth`) и CalDAV: обнаружение календарей через `PROPFIND`,
  выборка событий через `REPORT calendar-query`, запись — `PUT`/`DELETE` с iCalendar;
- фоновая синхронизация раз в 6 часов (WorkManager) и кнопки ручной синхронизации;
- очередь конфликтов с разбором по полям.

**Обновления**
- проверка новых версий через GitHub Releases (без токена): релиз с APK предлагается скачать,
  а подпись архива сверяется с установленным приложением, чтобы не подменить APK чужим.

## Как устроена синхронизация

Каждая локальная строка хранит **предка** — `syncBase`, снимок полей на момент последней успешной
синхронизации (`SyncSnapshot`: название, описание, начало, конец, напоминания, повтор). Решатель
`SyncConflictResolver` сравнивает предка, локальную версию и облачную и выбирает одно из действий:

| Решение | Когда | Что происходит |
|---|---|---|
| `Skip` | ничего не изменилось | ничего |
| `Insert` | локального события нет | строка создаётся без конфликта |
| `ApplyRemote` | менялось только облако | облачные значения применяются к строке |
| `AutoMerge` | стороны правили **разные** поля | правки объединяются, каждая остаётся |
| `Conflict` | стороны правили **одно и то же** поле | событие попадает в очередь конфликтов |
| `Purge` / `PushDelete` | событие удалено в облаке / локально | строка удаляется либо tombstone уезжает в облако |

Разбор конфликтов идёт на отдельном экране: по каждому спорному полю видно локальное и облачное
значение, выбор делается отдельно для каждого поля. Непересекающиеся правки уже слиты приложением,
а разобранное состояние становится новым предком — от него считаются дальнейшие изменения.

|---|---|
| ![Список конфликтов](docs/screenshots/conflicts.png) | ![Разбор конфликта](docs/screenshots/conflict-detail.png) |
| Очередь конфликтов | Разбор по полям: локальное значение против облачного |

**Удаления.** Google отдаёт удаления явными строками `DELETED=1` — для него состав коллекции не
нужен. CalDAV tombstone'ов не присылает, поэтому для Яндекса удаление определяется по отсутствию
события в **полной** выборке коллекции. Чтобы не удалить данные из-за неполного ответа:

- `CalDavClient` прерывается с ошибкой, если в `multistatus` есть не-2xx `propstat` с `calendar-data`;
- состав коллекции считается достоверным, только если разобраны все `VEVENT` из ответа;
- если в отчёте нет ни одного локально привязанного события, синхронизация считает, что попала в
  другую коллекцию, и ничего не удаляет.

Исчезнувшее событие разбирается тем же трёхсторонним решателем: если локально его не правили —
строка удаляется молча, если правили — открывается конфликт-удаление с выбором «удалить везде» или
«вернуть из облака» (восстановление берёт последний согласованный снимок).

## Визуальный язык

Экраны собраны на единой navy-палитре: тёмно-синие поверхности, светлый текст, слева на каждой
карточке события — цветная полоса провайдера. Карточки событий применяются во всех режимах;
недельный вид — столбец из семи карточек дней, пустой день остаётся карточкой только с
заголовком. Палитра, отступы, радиусы и типографика заданы токенами в
`presentation/theme/Tokens.kt` и `Type.kt` — это единый источник стилей и для будущего
Windows-приложения. Контраст пары «текст на поверхности» проверяется тестом `PaletteContrastTest`,
а соответствие схемы navy-палитре — `ThemePaletteTest` на устройстве.

Выходные и праздничные дни тонированы: тон выходного и тон праздника отличаются оттенком, а праздник
несёт ещё и форму-маркер у даты. Будни тоже получают собственный голубой тон, а все клетки обведены
видимой рамкой — сетка читается как набор отдельных карточек. Все пары контраста поверх этих тонов
зафиксированы тестом `PaletteContrastTest` — оттенок в сетку не попадает, пока текст и маркер на нём
не читаются.

## Архитектура

Слои разделены по пакетам `data` → `domain` → `presentation`; навигация — единственный
`NavHost`, экраны получают состояние из ViewModel. Синхронизация — это отдельный сценарий
`SyncRepositoryImpl`, который работает поверх `EventRepository`, `ConflictRepository` и
провайдеров календарей (`RemoteCalendarDataSource`).

```
app/src/main/java/com/example/mycalendar/
├── data/            Room, DataStore, сеть, CalDAV, CalendarContract, OAuth, аудио
├── domain/          модели (Event, SyncSnapshot, SyncConflict), репозитории, use case'ы
├── presentation/    Compose-экраны, ViewModel'и, тема, навигация
├── notifications/   уведомления, полноэкранное напоминание, «Отложить»
├── work/            планировщик будильников, SyncWorker, приёмник загрузки
└── di/              Hilt-модули
```

## Сборка

Требования: **JDK 17** и Android SDK с платформой **API 37**. Путь к SDK — в `local.properties`
(`sdk.dir=...`), файл в репозиторий не попадает.

```bash
./gradlew :app:assembleDebug          # debug APK
./gradlew :app:assembleRelease        # release с R8 и shrinkResources
./gradlew :app:testDebugUnitTest      # JVM-тесты приложения
./gradlew :shared:test                # тесты общего модуля (домен, слияние, синхронизация)
./gradlew :desktopApp:test            # тесты desktop-клиента
./gradlew :app:lintDebug              # Android Lint
./gradlew :app:connectedDebugAndroidTest  # тесты на подключённом устройстве/эмуляторе
./gradlew :desktopApp:createDistributable # образ Windows-клиента со встроенной JRE
./gradlew :desktopApp:packageMsi          # MSI-установщик (нужен WiX 3 в PATH)
./gradlew :desktopApp:packageExe          # EXE-установщик
```

**Сборка MSI.** Отдельно ставить WiX не нужно: плагин Compose сам скачивает WiX 3.11 в
`~/.gradle/compose-jb/wix311.zip` при упаковке (нужна сеть на первом запуске). `jpackage` из
JDK 21 умеет только WiX 3 (`candle.exe`/`light.exe`), поэтому внешний WiX 4+ не подойдёт;
проверено и с внешним WiX 3.14.1 в `PATH` (портативно в `%LOCALAPPDATA%\wix314`) — это запасной
вариант для сборки без сети. Артефакты — в
`desktopApp/build/compose/binaries/main/{msi,exe}/MyCalendar-0.1.0.msi` (около 107 МиБ каждый).
MSI ставит программу для всех пользователей (Windows запросит права администратора), кладёт
ярлыки на рабочий стол и в меню «Пуск» (группа `MyCalendar`); `upgradeUuid` закреплён в
`build.gradle.kts`, поэтому следующая версия обновляет установленную, а не встаёт рядом.

**Подпись release.** Ключ читается из `keystore.properties` в корне проекта:

```properties
storeFile=release.jks
storePassword=...
keyAlias=...
keyPassword=...
```

Оба файла (`keystore.properties`, `*.jks`) в `.gitignore` — ключи и пароли в репозиторий не
попадают. Без `keystore.properties` release собирается **неподписанным**; debug-ключ для релиза
не подставляется. Если пароль указывает на несуществующий файл или в файле не хватает полей,
сборка падает с понятной ошибкой.

## Ограничения

- Windows-клиент — в этом же репозитории: модуль `:shared` (домен, слияние, iCalendar,
  CalDAV-клиент, движок синхронизации) и заготовка
  `:desktopApp` на Compose Desktop с месячным видом: тона выходных и праздников, маркер праздника,
  точки событий по провайдерам (как на Android, не больше трёх на клетку), список событий
  выбранного дня под сеткой и фирменный градиент в шапке карточки события. Клик по карточке в
  списке дня открывает справа панель события: дата дня, время (открытая граница — многоточием),
  повтор, описание, заметка, метки, кнопки «Изменить» и «Удалить»; редактор открывается только
  из панели, а не по клику на карточку. Кнопка «+» в панели дня открывает редактор нового события:
  название, дата, время начала и конца, повтор; правка повторяющегося события меняет серию,
  удаление спрашивает подтверждение. Шестерёнка в шапке открывает настройки в духе Android:
  тема (системная / светлая / тёмная), тихий режим и сигналы напоминаний, флажок «Сворачивать в
  трей» — с ним крестик окна прячет программу в трей, а не завершает её (меню иконки: «Открыть»,
  «Выход»), версия и путь к данным. Настройки desktop-клиента хранятся файлом
  `%APPDATA%\MyCalendar\settings.json` (вне Windows — `~/.mycalendar/settings.json`); события — в
  `%APPDATA%\MyCalendar\events.json` (вне Windows — `~/.mycalendar/events.json`). Рядом лежат
  `conflicts.json` (очередь конфликтов) и `account.json` (учётные записи без токена): кнопка
  «Синхронизировать» в карточке «Календари» запускает общий движок на этих хранилищах, а строка
  под ней показывает итог в формулировках Android («Готово: отправлено …, получено …, конфликтов …»)
  или время последней синхронизации после перезапуска. Открытая очередь видна там же строкой
  «Конфликты: N» с кнопкой «Разобрать»: экран разбора повторяет Android — слева список конфликтов,
  справа выбранный; спорные поля переключаются чипами «Локальное»/«Из облака», удаления
  разбираются исходами «Удалить везде» (с подтверждением) и «Вернуть из облака»/«Создать заново
  в облаке». Перед записью очередь перечитывается: если она успела измениться, выбор не применяется
  и экран объясняет, что конфликт нужно открыть заново. Вход через
  Яндекс работает по коду устройства: карточка «Яндекс» в настройках
  показывает код, копирует его и открывает `https://ya.ru/device` в браузере, приложение опрашивает
  токен до истечения кода (5 минут); токен живёт только в памяти, без записей на диск и в файлы.
  Напоминания desktop-клиент доставляет, пока сам запущен: при старте расписание строится по
  будущим событиям, сохранение и удаление события перепланируют его, а в момент срабатывания
  вверху окна появляется плашка «Начало в 09:30 (через 5 мин)» с кнопками «Открыть» (переход
  к дню события) и «Закрыть», окно разворачивается из трея и играет сигнал — выбранный файл,
  если формат WAV/AU/AIFF, иначе системный писк; в тихом режиме плашка молчит. Повторяющееся
  событие после срабатывания сразу планирует следующее вхождение. Откладывания нет, автозапуска
  с Windows нет, и при закрытой программе напоминание не придёт.
- Обновления ищутся в GitHub Releases репозитория `zanzibara82/calendar`: пока релиз не опубликован,
  приложение честно отвечает «Опубликованных релизов пока нет».
- Google-синхронизация работает через системный календарь, поэтому требует добавленного аккаунта
  Google на устройстве; OAuth-клиент и регистрация в Google Cloud Console не нужны.
- Для Яндекса нужен `YANDEX_CLIENT_ID` в `data/auth/OAuthConfig.kt` и приложение, зарегистрированное
  в Яндекс OAuth с callback `mycalendar://oauth`.
