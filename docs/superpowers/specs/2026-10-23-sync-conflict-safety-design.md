# Сохранность данных при конфликтах синхронизации — дизайн

Дата: 2026-10-23. Статус: одобрен пользователем (разделы 1–5 — «одобряем», симметричный
tombstone — «оставляем»). Путь: архитектурный (`superpowers:brainstorming`).

## Контекст и требование

ТЗ SyncPlanner v1.0:

- §7 «Не перезаписывай данные молча»;
- §21.9 «Конфликты не приводят к незаметной потере данных»;
- §10 «собственные теги и заметки хранятся в собственной БД приложения»;
- §23 требует `architecture.md` — этот файл описывает часть про сохранность данных при
  синхронизации и закрывает её.

Сейчас при пересечении правок побеждает более свежий `updatedAt` (last-write-wins),
проигравшая версия теряется безвозвратно
([SyncConflictResolver.kt:22-25](../../../app/src/main/java/com/example/mycalendar/data/repository/SyncConflictResolver.kt)),
а в [SyncResult](../../../app/src/main/java/com/example/mycalendar/domain/repository/SyncRepository.kt)
едёт только счётчик `conflicts` — пользователь не видит ни что именно столкнулось, ни вторую версию.

Для Google-синхронизации через системный календарь (`CalendarContract` нет колонки
«изменено в») конфликты вообще разрешались эвристикой `sameContent`
([SyncRepositoryImpl.kt:282-288](../../../app/src/main/java/com/example/mycalendar/data/repository/SyncRepositoryImpl.kt)):
«содержимое похоже — значит, моих правок нет». Локальные поля (метки, текстовая и голосовая
заметки) уже защищены переносом из локальной записи (`Event.appliedTo`) — этот механизм
остаётся и в новом дизайне.

## Раздел 1. Модель данных

**Инвариант.** `syncBase` — последнее состояние, в котором локальная запись и облако согласны
друг с другом. Хранится только по синхронизируемым полям: `title`, `description`, `startTime`,
`endTime`, `reminderMinutes`, `repeatRule`. Поля `tags` / `textNote` / `voiceNotePath` в снимок
не попадают принципиально: они не могут быть «спорными», и их защищает единственный механизм —
`appliedTo`.

- В таблице `events` одна колонка `syncBase TEXT` (nullable, JSON через kotlinx.serialization).
  Предок лежит рядом с записью, а не в отдельной таблице: `pendingSync` / `isDeleted` / `remoteId`
  уже живут в этой строке, разделение sync-состояния и контента в схеме нарушено, и вводить
  вторую сущность ради одной колонки дороже, чем выиграть.
- Новая таблица `sync_conflicts`: `id`, `eventId` (уникальный индекс — не больше одного открытого
  конфликта на событие), `provider`, `remoteId`, `base`, `remote` (снимки), `contestedFields`,
  `kind`, `detectedAt`.
- `kind: ConflictKind` = `CONTENT` | `REMOTE_DELETED` | `LOCAL_DELETED` — вместо булева
  `remoteDeleted`, потому что случай с локальным tombstone симметричен облачному удалению.
- `local` в таблице не храним: конфликт разбирается против **текущего** значения строки. Иначе
  пользователь, отредактировавший событие пока конфликт открыт, получил бы разбор против
  устаревшей копии, а его свежая правка оказалась бы проигравшей.
- Миграция Room 2 → 3: колонка + таблица + уникальный индекс; `app/schemas/…/3.json`.
- FK `eventId → events.id` с `ON DELETE CASCADE`: удалили событие вручную — строка конфликта
  уходит сама, разбирать нечего.

## Раздел 2. Алгоритм мержа

`remoteChanges = diff(base, remote)`, `localChanges = diff(base, текущая локальная)`.
Напоминания сравниваются как множество, а не как список (текущий `sameContent` учитывал это).

| Ситуация | Действие |
|---|---|
| `remoteChanges` пуст | ничего не трогаем (сегодня замена происходит именно тут по неверному признаку) |
| `localChanges` пуст И `pendingSync == true` | локальная запись равна предку, но её состояние (правка, возврат из облака или tombstone) ещё не подтверждено облаком — молча заменять её нельзя, ждём push |
| `localChanges` пуст | применяем облако, `syncBase := remote` |
| поля не пересекаются **или пересекаются, но значения уже одинаковые** | применяем облачные изменения поверх локальных (только то, чего локально ещё нет), `pendingSync := true` (результат надо отправить), `syncBase` **не** двигаем; если объединять нечего — `Skip` |
| пересечения есть и значения различаются | непересекающиеся объединяем молча, по спорным — строка в `sync_conflicts`, локальное значение остаётся в силе |
| `syncBase == null`, `pendingSync == false` | предком считается текущее состояние, облако применяется молча |
| `syncBase == null`, есть неотправленные правки | все различающиеся поля спорные |

**Спорным поле считается только когда значения реально различаются.** Формально
`contested = remoteChanges ∩ localChanges`, но если после объединения локальная запись уже
равна облачной по всем полям, конфликта нет: повторный pull до успешного push должен быть
идемпотентен, а не плодить тот же конфликт заново.

**Почему предок не двигается при авто-мерже.** Если сдвинуть `syncBase` до успешного push, то
упавшая отправка превратит следующую правку облака в «локальных изменений нет», и она придёт
молча поверх неотправленного. Поэтому `syncBase` сдвигается ровно в четырёх местах: применение
облака (`ApplyRemote`, `Insert`), успешный push (`markSynced`, `attachToProvider`) и разбор
конфликта пользователем (`saveResolved`).

Разбор — четвёртое место не случайно: выбранное пользователем значение и есть новое согласованное
состояние, от которого дальше считается `localChanges`. Если бы предок при разборе не двигался,
то при порядке «pull раньше push» следующий pull сравнил бы облако (со старым значением) с локалом
(с новым) относительно того же предка, снова увидел пересечение и воскресил тот же конфликт —
разбор нельзя было бы сделать вообще. Движется именно снимок **после** разбора: он выражает намерение
пользователя, а push лишь доставляет его в облако.

**Дополнительное правило (следствие «локальное значение остаётся в силе»).** Пока у события
открыт конфликт, фаза PUSH его пропускает. Иначе следующий пуш молча перезаписал бы спорные
поля облачной стороны — ровно то, что запрещает §7.

**PULL события с открытым конфликтом не пропускается — он обновляет существующую строку.**
Конфликт живёт в таблице, а не в потоке данных: повторное пересечение должно принести в строку
свежий снимок облака (`ConflictRepository.save` переиспользует `id` по `eventId` и делает upsert),
чтобы пользователь разбирал актуальное состояние, а не то, что устарело. Дубликата не возникает —
этого же требует уникальный индекс на `eventId`.

Точка входа — одна чистая функция
`SyncConflictResolver.decide(record: SyncedRecord?, remote: RemoteEvent, provider: CalendarProvider): PullDecision`.
Класс сохраняется как фасад (как и договаривались), но LWW-метод `resolve(local, remote)` и
enum `Resolution` уходят: вместо них — sealed `PullDecision` —
`Skip` / `Insert` / `ApplyRemote` / `AutoMerge` / `Conflict` / `Purge` / `PushDelete`.
Так решение «молча применить или в очередь» становится проверяемым на JVM без Android-зависимостей.

Эвристика `sameContent` и сравнение по `updatedAt` в `doSync` удаляются: на вопрос «кто
изменился» отвечает предок. Свойство `RemoteCalendarDataSource.hasReliableUpdatedAt` остаётся
как описание возможности инкрементального pull, но в разрешении конфликтов больше не участвует.

## Раздел 3. Удаления и голосовой файл

- **Локальный tombstone + изменённое в облаке**: push НЕ вызывает `remote.delete`, строка
  остаётся с `isDeleted = 1`, создаётся конфликт `LOCAL_DELETED`. Исходы: «удалить везде» →
  закрыть конфликт, дальше работает tombstone-путь push (delete в облаке, потом `purge` —
  строка вместе с файлом); «вернуть из облака» → `isDeleted = 0`, синхронизируемые поля из
  облака, `pendingSync = 1`.
- **Удалено в облаке + локально есть неотправленные правки**: `hardDelete` не выполняется, файл
  не трогается, конфликт `REMOTE_DELETED` с теми же двумя исходами. «Удалить везде» здесь —
  немедленный purge (облако уже без события); «вернуть из облака» — снять `remoteId`, чтобы push
  пересоздал событие в облаке.
- **Возврат из облака передвигает предка** на снимок облака: после возврата локальная запись равна
  облачной, и следующий pull обязан уйти на ветку «`pendingSync == true` — ждём push», а не
  воскресить тот же конфликт. При «удалить везде» предок уходит вместе со строкой.
- **Удалено в облаке, локальных правок нет**: тихий purge — это не потеря данных, предок и
  локальная запись совпадали.
- **Локальный tombstone, облако не менялось**: push удаляет как сейчас. Если снимка-предка нет
  (строки до миграции), доказательств независимой правки в облаке нет — удаление не блокируется.
- **Инвариант файла**: файл `.m4a` удаляется ровно тогда и только тогда, когда удаляется строка
  БД. Сегодня [DeleteEventUseCase.kt:100-104](../../../app/src/main/java/com/example/mycalendar/domain/usecase/EventUseCases.kt)
  сносит файл до подтверждения облачного удаления, а `hardDelete` в фазе push файла не чистит
  вовсе. Исправление: `DeleteEventUseCase` делает только tombstone, чистка файла живёт рядом с
  `hardDelete` в синхронизации (один приватный `purge`).
- Все события пережили синхронизацию → файл цел. Строки нет → файла нет.

## Раздел 4. UI и слои

- [SettingsScreen.kt](../../../app/src/main/java/com/example/mycalendar/presentation/settings/SettingsScreen.kt) —
  под блоком карточек календарей строка «Конфликты: N» (`Flow<Int>` из
  `ConflictRepository.observeOpenCount()`), при нуле не показывается. Тап →
  `Screen.Conflicts` (`"conflicts"`).
- `ConflictListScreen` — заголовок события, дата, бейдж провайдера, «N спорных полей» или текст
  про удаление. Тап → `Screen.ConflictDetail` (`"conflict/{conflictId}"`).
- `ConflictDetailScreen` — по каждому спорному полю две карточки (локальная / облачная) с выбором
  значения, кнопка «Применить»: выбранные значения пишутся в событие, `pendingSync = 1`,
  `syncBase` принимает снимок разобранного состояния (метод `saveResolved`), строка конфликта
  удаляется. Для `REMOTE_DELETED` / `LOCAL_DELETED` вместо пикера — те же две кнопки из
  раздела 3.
- Слои как в проекте: `domain/model/{SyncSnapshot,SyncConflict,SyncedRecord}.kt`,
  `domain/repository/ConflictRepository.kt`, `domain/usecase/ResolveConflictUseCase.kt`,
  `data/local/{SyncConflictEntity,SyncConflictDao}.kt`, `data/repository/ConflictRepositoryImpl.kt`,
  `presentation/conflict/*`. Реестра разрешений и истории не заводим.

## Раздел 5. Тесты, границы, сознательные исключения

- JVM (`SyncConflictResolverTest`) — полная таблица раздела 2: предок пуст / облако не менялось /
  локально не менялось / локально не менялось, но есть неотправленное состояние (`Skip`) / дизъюнкт /
  пересечение / пересечение с уже одинаковыми значениями (`Skip`, идемпотентность повторного pull) /
  `base == null` при `pendingSync` и без него / напоминания как множество / оба вида удалений.
- JVM (`SyncSnapshotTest`) — round-trip снимка: кириллица, переводы строк и запятые в
  `description`; наложение выбранного поля на событие.
- JVM — `EventRepositoryImpl` и `ConflictRepositoryImpl` с подставным DAO: `saveFromUser`
  сохраняет `syncBase`, `saveFromRemote` пишет предка, `save` конфликта не плодит вторую строку
  на то же событие.
- androidTest — `Migration2to3Test`: схема после миграции совпадает с `3.json`, старые события
  целы, `syncBase` у них null.
- androidTest — сквозной: фиксованный `RemoteCalendarDataSource` + настоящая Room; pull с
  пересечением → событие не перезаписано и конфликт создан ровно один; разбор → `pendingSync = 1`
  и предок = разобранное состояние; повторный pull с тем же облаком не создаёт второй конфликт и
  не воскрешает разобранный; спорные поля не уходят в push, пока конфликт открыт.
- Сейчас в JVM-суите 22 теста. 19 из них (ICS, повторения, перенос локальных полей) не меняются и
  обязаны остаться зелёными; 3 теста `SyncConflictResolverTest` переписываются, потому что LWW
  уходит.

**Сознательно не делаем** (отложлено, вне объёма этой задачи): собственный сервер синхронизации и
операции с ID/курсором (§7 ТЗ), ETag / `If-None-Match` в CalDAV, слияние внутри одного поля
(два разных описания не склеиваем), массовый разбор конфликтов, UI-история разрешённых конфликтов,
`values-en`.
